# driver-app/ios/.xcode.env

## 1. Purpose
A tiny shell file that Xcode sources (loads) before it runs build script phases. It tells Xcode where `node` is, because Xcode does not use your shell profile. The build phase "Bundle React Native code and images" needs node to make the JS bundle.

## 2. Imports, one by one
No imports. Only one command is used: `command -v node` (line 11). It is a shell built-in that prints the full path of a program. *Example:* it prints `/home/user/.local/share/mise/shims/node`.

## 3. Walk through the code, top to bottom
- Lines 1-10 are comments (`#`). They say the file is versioned in git, and that personal changes go in `.xcode.env.local`, which is not versioned.
- `export NODE_BINARY=$(command -v node)` (line 11).
  - `$(...)` runs the inner command and pastes its output.
  - `export` makes the variable visible to child programs, such as the build scripts.
  - Result: `NODE_BINARY` holds the path of the first `node` found in PATH.

Error case: if node is not in PATH when Xcode runs, the variable is empty and the bundle step fails.

## 4. How data flows
```
Xcode build -> sources .xcode.env -> NODE_BINARY=/path/to/node
            -> RN bundle script runs "$NODE_BINARY ..." -> main.jsbundle
```

## 5. Try it
```zsh
cd driver-app/ios
bash -c '. ./.xcode.env; echo "$NODE_BINARY"'
```
`bash -c` runs a string as a script; `.` sources the file; `echo` prints. Expected: a path to node. iOS builds need macOS, so on your Arch machine this file is only for reading.

## 6. Can it be better?
- Good: template default, easy to override.
- Weak: with version managers like mise or nvm, the PATH Xcode sees may differ, so a wrong node may be used. A team mate on another setup needs `.xcode.env.local`.
- Cleaner way: pin the path in `.xcode.env.local` per machine.
- Security: nothing risky.
