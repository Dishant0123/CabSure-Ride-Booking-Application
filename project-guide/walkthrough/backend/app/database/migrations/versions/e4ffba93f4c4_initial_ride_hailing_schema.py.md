## 6. Can it be better?
- Good: strong integrity (foreign keys, checks, uniques), money as integers, idempotency key on payments, useful composite indexes, soft delete.
- Weak: auto-generated, so it carries the "please adjust" comments. Status strings plus check constraints must be edited with a new migration whenever a status is added (see `g5b0d4e80001`). `ride_categories` and `vehicles.category_code` are linked by text, not a foreign key. `fare_line_items` has no `created_at`. `drivers.email` unique allows many NULLs (fine on PostgreSQL and SQLite). Statuses duplicated in model code and here can drift.
- Cleaner way (opinion): link `vehicles` to categories by id, or make `category_code` a foreign key to `ride_categories.code`.
- Security: stores hashes, not raw passwords, OTP codes or refresh tokens. Good. Document files are stored as a `storage_key`, not content.
